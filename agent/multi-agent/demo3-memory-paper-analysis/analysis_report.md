### 0.1 PersonaMem
#### 0.1.0 动态偏好演变追踪（Dynamic Preference Evolution Tracking）

这是 PersonaMem 的**核心创新点**，指的是用户的偏好/特征会随时间发生变化，模型需要从交互历史中识别并跟踪这种变化。
**具体机制：**
论文将用户画像分为两层：
- **静态属性（Static Profile）**：姓名、年龄、性别、种族、职业等基本不变的人口统计信息
- **动态属性（Dynamic Profile）**：个人经历、性格特征、偏好等**会随时间演变**的特征

**评测设计：** 每个问题给出 **4 个候选回复**，只有 1 个符合用户**当前状态**，其余 3 个干扰项包含：
- **过时偏好**（如：用户已经不吃麸质了，但回复仍按旧偏好推荐意面）
- **无关信息**（与该用户无关的泛化回答）
这就逼迫模型必须在长达数十个 session 的交互历史中，**准确定位到偏好发生变化的时间点**，并以最新状态作答——而非简单地召回"出现频率最高"或"最早出现"的偏好。

#### 0.1.1 四选一判别+生成两种评测模式
论文设计了两种互补的评测方式：
##### 模式 A：判别式（Discriminative Setting）— 主评测
```
输入：用户交互历史 + 当前查询 + 4 个候选回复 (a)(b)(c)(d)（随机排序）
输出：模型选择最合适的选项 + 简要解释

示例：
  问题：用户问"Can you recommend a recipe for tonight?"
  (a) 推荐意面（过时偏好）
  (b) 推荐地中海烤鱼（当前偏好）  ← 正确答案
  (c) 推荐泛化的快手菜（无关）
  (d) 推荐日料（无关）
```
模型需要在看到所有选项后，**选出唯一符合用户当前状态的回复**。这种方式评测简洁、可自动计算准确率、不依赖 LLM judge。论文对 15 个前沿模型在 128k 和 1M 上下文下做了系统评测。

##### 模式 B：生成式（Generative Setting）— 辅助评测
```
输入：用户交互历史 + 当前查询（不展示候选）
方法：分别计算模型对 4 个候选回复的 log-sum token probability（带长度归一化）
输出：选择概率最高的那个作为模型回答
```
关键区别：
- 模型**看不到候选选项**，不是在做"选择题"
- 而是通过计算"模型更倾向于生成哪个回复"来间接评测 【生成式模型：逐个token预测下一个token的概率，对于候选回复，模型可计算：给定上下文，!!#cc0000 生成这段候选回复的概率!!】
- 需要访问模型的 **logits（词表概率分布）**，因此只能用于开源模型（闭源 API 通常不暴露 logits）

**两种模式的对比发现：** 在 Llama-3.1-8B 上，生成式准确率**反而高于**判别式——暗示模型"知道该怎么回复"但在**显式选择题中反而容易被干扰项误导**。不过生成式目前仅在 32k 上下文上验证，更长上下文和更多模型上是否一致还有待研究。

### 0.2 LongMemEval
#### 0.2.0 五大评测维度
##### Information Extraction（信息抽取，IE）

从大量交互历史中**召回特定信息**的能力，包括用户或助手提到的细节。
>例：用户曾说"我每天通勤听有声书，单程 45 分钟" → 问"我的通勤时间多长？" → 答"单程 45 分钟"

##### Multi-Session Reasoning（跨 Session 推理，MR）

**综合多个对话 session 的信息**来回答需要聚合或比较的复杂问题。
>例：用户在不同 session 分别提到拥有 Korg B1 钢琴、Fender 电吉他、Yamaha 木吉他、Pearl 鼓 → 问"我目前有几件乐器？" → 需要跨 session 汇总得出 "4 件"

##### Knowledge Updates（知识更新，KU）

识别用户个人信息**发生了变化**，并动态更新对用户的认知。
>例：用户先说"上个月全家去了夏威夷浮潜"，后来又说"上周全家去了巴黎" → 问"我最近一次家庭旅行去了哪？" → 必须答"巴黎"而非"夏威夷"

##### Temporal Reasoning（时间推理，TR）

对用户信息的**时间维度**保持感知，包括对话中的显式时间提及和 session 的时间戳元数据。
>例：用户说"今天去了科学博物馆的幕后参观"、另一次说"上周参加了画展开幕式" → 问"我最近参加的活动是什么？" → 需要结合 session 时间戳推理先后顺序

##### Abstention（拒答，ABS）

识别**用户从未提及的信息**，并回答"我不知道"，而非编造答案。
>例：从已有问题中修改出"虚假前提"问题（用户从未提到过的事） → 模型应拒答而非幻觉生成

#### 0.2.1 关键设计

论文基于这 5 大能力设计了 **7 种题型**：

|题型|对应能力|说明|
|:-:|:-:|:-:|
|single-session-user|IE|召回用户在单个 session 中提到的信息|
|single-session-assistant|IE|召回助手在单个 session 中提到的信息|
|single-session-preference|IE|利用用户信息生成个性化回复|
|multi-session|MR|跨多个 session 聚合信息|
|knowledge-update|KU|识别用户信息的变化|
|temporal-reasoning|TR|结合时间戳和时间引用推理|
|false-premise（虚假前提）|ABS|识别问题所问信息从未出现，拒绝回答|

共 **500 道精标问题**，嵌入可自由扩展的对话历史（约 115k tokens 的 S 版和 ~1.5M tokens 的 M 版）

#### 0.2.2 三阶段优化
##### Stage 1: Indexing（索引/建库）

>把每轮历史对话转换成一条或多条键值对存入记忆库

**控制点 CP1 — Value（存什么）：** 每条记忆的格式和粒度
- 粗粒度：整个 session 存为一条 → 检索和阅读都困难（一个 session 通常涉及多个话题）
- 中粒度：拆成单轮对话（round）→ **论文推荐，效果最好**
- 细粒度：压缩为摘要或事实 → 可能丢失细节

**控制点 CP2 — Key（怎么索引）：** 用什么作为检索的"标签"
- 最简单：Key = Value（直接用内容本身做向量检索）
- 论文优化：**Fact-Augmented Key Expansion** — 用 LLM 从每轮对话中提取关键事实，将事实追加到 Key 中。这样即使用户的问法和原文措辞完全不同，也能通过事实匹配命中

##### Stage 2: Retrieval（检索）

>根据用户问题，从记忆库中找出最相关的条目

**控制点 CP3 — Query（用什么查询）：** 如何构造检索 query
- 最简单：直接拿用户问题做 query
- 论文优化：**Time-Aware Query Expansion** — 当问题涉及时间（"最近""上个月"），自动在 query 中注入时间范围信息，缩小搜索范围。例如"我最近一次家庭旅行"→ 自动补充"2024年10-11月"来限定检索

##### Stage 3: Reading（阅读/生成）

>LLM 阅读检索到的记忆条目，生成最终回答

**控制点 CP4 — Reading Strategy（怎么读）：** LLM 如何利用检索结果
- 直接读（direct）：把检索到的文本拼入 prompt，直接让 LLM 回答
- 论文优化：**Chain-of-Note (CoN) + 结构化 JSON 格式**
	- 先让 LLM 从每条记忆中**提取关键信息做笔记**
	- 再基于笔记推理回答
	- 用 JSON 格式呈现记忆条目，帮助模型清晰区分各条记忆的边界


 ### 0.3 **KnowMe-Bench**
 
 #### 0.3.0 分层评测
核心创新在于：**不把记忆评测当作"信息检索"问题，而是当作"理解一个人"的问题**。
分层后，可以精确诊断：**你的系统是"能记住但不能推理"，还是"能推理但记不准"**。
论文将"理解一个人"的能力按照**认知深度**分为三个递进层级：
 
 ##### Level I：Fact & Entity（事实与实体层）— "能回忆"

最基础的层级，考察模型能否从长篇自传叙事中**提取具体事实**。

|题型|说明|示例|
|:-:|:-:|:-:|
|**T1: Detail Extraction（细节提取）**|提取叙事中的具体事实：地点、时间、人物属性等|"主人公第一次搬家是搬到哪个城市？"|
|**T2: Entity Tracking（实体追踪）**|追踪某个实体在叙事中的状态变化，**包括识别"从未出现"的实体并拒答**|"角色 X 在第三章中的职业是什么？"（如果从未提及，应拒答）|
>**特点：** 答案是明确的、可验证的事实。评分标准看 **实体准确性** 和 **值精度**。
 
 
 ##### Level II：Temporal Logic（时序逻辑层）— "能推理"

中间层级，需要**跨越时间线进行因果推理**，不能只靠单点记忆。

|题型|说明|示例|
|:-:|:-:|:-:|
|**T3: Temporal Ordering（时间排序）**|判断事件发生的先后顺序，特别是在有**闪回（flashback）**打乱叙事顺序时|"主人公是先失业还是先离婚？"（叙事中先讲了离婚的回忆，但实际事件中失业在先）|
|**T4: Causal Relation（因果关系）**|识别事件之间的因果链|"是什么事件直接导致主人公决定搬到巴黎？"|
|**T5: Contextual Reasoning（上下文推理）**|需要结合多处上下文的信息进行推理|"主人公为什么在那个特定时间点改变了对父亲的看法？"|

 ##### Level III：Insight（洞察/心理分析层）— "能理解"

最难的层级，要求模型像文学评论家或心理分析师一样**深入理解人物的内在世界**。

|题型|说明|示例|
|:-:|:-:|:-:|
|**T6: Mind-Body Interaction（身心互动/反讽行为）**|解释人物**外在行为与内在状态之间的矛盾或反讽**，比如"嘴上说没事但行为暴露了真实感受"|"主人公声称对分手毫不在意，但他接下来几周的行为模式说明了什么？"|
|**T7: Expert-Annotated Psychoanalysis（专家级心理分析）**|由文学专家撰写的开放式深度问题，涉及**动机、身份认同、核心隐喻**|"主人公反复提到的'边界消融'意象，如何与他的自我认同危机相呼应？"|
>**特点：** 答案不是事实，而是**解释性的洞察**。评分看 **外在→内在映射的准确性**，只有捕捉到参考答案中定义的**核心隐喻/心理机制**才能得满分，泛泛的"情绪描述"不行。

 #### 0.3.1 证据约束
 与其他 benchmark 最大的区别在于：**Level II 和 Level III 的回答必须附带证据**。
```
模型输出 = {
  "inference": "简洁的推理结论",
  "evidence_set": ["事件A（时间点X）", "事件B（时间点Y）", ...]  ← 必须指出支撑结论的具体事件
}
```
这意味着模型不能"自由联想"——如果回答"主人公因为童年创伤所以害怕亲密关系"，必须指出**具体哪些事件**支撑了这个结论。这防止了 LLM 的幻觉和无根据的泛化推断。

#### 0.3.2 闪回/非线性时间处理
叙事顺序 != 事件发生顺序
论文在构建 benchmark 数据时，设计了一套精巧的**闪回感知时间重对齐机制**（Stage III），把打乱的叙事还原成真实时间线：
##### 核心概念：将每个闪回拆成两部分
```
一段闪回文字 = 事件内容（Cevent） + 记忆触发器（Ttrigger）
                  ↓                      ↓
          归位到历史时间点            留在当前意识流中
```
用栈来实现还原一个真实的时间线
|动作|含义|
|:-:|:-:|
|**MAINTAIN**|继续当前时间线，不跳转|
|**PUSH(t_new)**|进入闪回 — 把事件内容归位到新时间点 t_new|
|**POP()**|闪回结束 — 回到上层时间线|
|**TRANSIENT**|一闪而过的联想（比如"这让我想起了……"但没有展开叙述），标记触发器但不改变栈|



### 0.4 **LOCOMO**
#### 三个递进的任务
**不仅要"记住事实"，还要"理解因果"，更要"表现出来"**
##### Task 1：Question Answering（问答任务）

直接"考试"模型的记忆能力。总共 **7,512 道题**，分为 5 种推理类型：

|类型|占比|含义|示例|
|:-:|:-:|:-:|:-:|
|**Single-hop**|36%|答案在**单个 session** 中就能找到|"Nate 的宠物叫什么？"|
|**Multi-hop**|14.6%|需要**跨多个 session** 合成信息|"Joanna 参加的两个比赛结果分别如何？"（分别在第 3 和第 12 个 session 讨论过）|
|**Temporal**|20.6%|需要**时间推理**，捕捉对话中的时间线索|"Nate 是先养狗还是先搬家？"|
|**Open-domain**|3.9%|需要把对话中的信息**与外部常识结合**|"Joanna 对动物毛过敏，她能养什么宠物？"（需要常识：乌龟/鱼没有毛）|
|**Adversarial**|24.9%|**故意设陷阱**的题，正确答案是"无法回答"|详见下面第三部分|

##### Task 2：Event Graph Summarization（事件图总结任务）

这是 LOCOMO 最独特的任务。模型需要**从对话历史中提取出一个人的完整人生事件图**，包括：
- 每个事件的内容
- 每个事件发生的时间
- 事件之间的**因果关系**

然后和 ground truth 的事件图 G 做对比。评测用 **FactScore**（!!#cc0000 原子事实分解!!），分别算 precision 和 recall：
```
模型输出的事件图                    Ground truth 事件图 G
┌───────────────────┐           ┌───────────────────┐
│ 1月: 赢了电竞比赛    │           │ 1月: 赢了电竞比赛    │  ✅ 命中
│ 2月: 买了新狗        │  比较→     │ 2月: 领养了狗         │  ⚠️ 细节偏差(买→领养)
│ ❌ 遗漏              │           │ 3月: 和邻居的狗约玩   │  ❌ 召回失败
│ 4月: Joanna写了剧本  │  ←───     │ 这是 Nate 的事件图！  │  ❌ 说话人归因错误!
└───────────────────┘           └───────────────────┘

```
##### Task 3：Multi-modal Dialogue Generation（多模态对话生成）

最接近实际应用的任务。给定之前的对话历史，模型需要**生成下一轮对话（包含文字和图片）**，而且必须：
- 和说话人的 **persona 一致**（比如 Joanna 对动物毛过敏，就不应该建议她养猫）
- 和之前的**事件发展连贯**（如果上次说受伤了，这次不应该聊极限运动）
- 分享的**图片与对话内容相关**

#### 数据来源（两个LLM生成+人类标注）
数据生成约束：  
- Persona 约束：每个 Agent 有一个详细的人物画像 `p`
- 每个 Agent 还有一个**时间事件图 G**，由 LLM 根据 persona 生成。
```
Joanna (说话人 1):
- 28岁女性，住在纽约
- 职业：自由编剧
- 爱好：写作、读书、看电影（偏好文艺片）、探索自然
- 特征：对大部分有毛动物过敏
- 社交关系：有几个亲密朋友，单身

[
  {"id": "e1", "event": "赢了CS:GO电竞比赛", "date": "2022-01-15", "caused_by": []},
  {"id": "e2", "event": "领养了一只小狗", "date": "2022-02-10", "caused_by": ["e1"]}
]

Persona → 决定 "这个人会说什么样的话"
Event Graph → 决定 "这个人在什么时间经历了什么事"
两者结合 → 生成出有时间跨度、有因果链、人设一致的超长对话
```

#### 对抗题
对抗题是**故意设计成"看起来能回答，但其实无法回答"的问题**，正确答案是**"unanswerable（无法回答）"**。
核心手法：**说话人错绑（Speaker Attribution Error）** 和 **事件错绑（Event Misattribution）**
目前测试结果：**!!#cc0000 上下文越长，对抗题表现越差!!！** (GPT-3.5-turbo 在 4K 上下文时得 12.8%，扩到 16K 后**暴跌到 2.1%**)。

```
对话历史中的事实：
  - Nate 赢了电竞比赛（Nate 说的）
  - Joanna 写完了剧本（Joanna 说的）

对抗题：
  ❓ "Joanna 赢了什么电竞比赛？"
  
  → 正确答案：无法回答（unanswerable）
  → 因为赢电竞比赛的是 Nate，不是 Joanna
```


### 0.5 Mem-Gallery
#### 三大维度，9个子任务
**先"存得准"，再"想得通"，最后"管得住"**

##### 维度 1：记忆抽取与适应（Memory Extraction & Adaptation） — 50.4%

这是基础能力：**你存进去的东西能不能准确取出来，并且随着新信息到来能适应？**

|子任务|缩写|QA数|平均线索数|含义|
|:-:|:-:|:-:|:-:|:-:|
|**Factual Retrieval**|FR|219|2.90|回忆对话中提到的**事实**（用户偏好、事件、决定）|
|**Visual-centric Search**|VS|306|1.91|从记忆中**检索/定位正确的图片**|

## 1. Benchmark：memory 评测维度的关键区别（重点对比）

### 1.1 评测对象：从"能检索"到"能追踪演变、能管理、能解释"
- **PersonaMem**：聚焦 *动态用户画像与个性化响应*，核心考察 LLM 能否从长期交互历史中 **(1) 内化用户特征与偏好，(2) 追踪偏好随时间的动态演变，(3) 据此生成个性化回复**。180+ 用户画像 × 15 个真实任务（写作建议、旅行规划、心理咨询等）× 最多 60 sessions，评测以四选一判别为主（仅一个选项符合用户**当前**状态，其余含过时/无关偏好），前沿模型仅约 50%——揭示"偏好演变追踪"是当前 LLM 的显著短板。
- **LongMemEval**：面向 *chat assistant 产品形态* 的长期交互记忆，覆盖 **信息抽取/跨 session 推理/时间推理/知识更新/拒答**，并强调**全流程可诊断**（indexing-retrieval-reading）。
- **Mem-Gallery**：把 LongMemEval 的"全流程"进一步扩展到 **多模态**，并将"长期记忆"拆成三大功能维度：  
  **抽取&适应（FR/VS/TTL）—推理（TR/VR/MR）—知识管理（KR/CD/AR）**。
- **KnowMe-Bench**：评测目标上移到"**人理解（person understanding）**"，不仅问"记住什么"，还问"**为什么**（动机/原则）"，并用 **evidence set** 抑制无依据推断。
- **LOCOMO**：更像"超长对话理解能力综合测试"，强调 **时间/因果链**与对话一致性，附带多模态互动，但其多模态在任务中未必像 Mem-Gallery 那样"必须用视觉才能解"。

### 1.2 数据形态与时间结构：对话 vs 自传叙事 vs 多模态对话
- **PersonaMem**：基于结构化 persona（含人口统计+个人经历+动态偏好）自动生成的多 session 用户-LLM 交互历史。独特之处在于 **按拓扑排序的 session 拼接**机制，保证因果一致性的同时允许多种合法交错顺序，并插入"无关闲聊"模拟真实使用模式。上下文长度可达 128k~1M tokens。
- **LongMemEval**：任务型人机对话，历史长度可扩展（~115k / ~1.5M tokens），更接近"现实助手日志"。
- **LOCOMO**：长对话（~9k tokens/对话，~19 sessions 平均，最多 35），以 persona+event graph 约束提升长程一致性，并加入图片分享/反应行为。
- **KnowMe-Bench**：自传叙事天然含"闪回/心理时间旅行"，通过 **mnestic realignment** 将"回忆内容"放回其真实时间锚点，显式解决非线性时间导致的归因错误。
- **Mem-Gallery**：多 session 多模态对话，任务设计强调视觉线索对检索/推理的关键性，并指出多模态 memory 的存储检索成本显著。

### 1.3 是否考察"更新/冲突/拒答"（真实系统不可回避的能力）
- **强覆盖**：LongMemEval（knowledge updates + abstention）、Mem-Gallery（KR/CD/AR）。
- **偏好演变专项**：PersonaMem — 四选一干扰项中混入**过时偏好**和**无关信息**，直接测量模型是否能识别"偏好已更新"而非沿用旧记忆，本质上是"更新检测"的个性化版本。
- **弱覆盖/非主轴**：LOCOMO（更偏因果/时间理解与生成一致性）、KnowMe-Bench（强调 evidence 约束，但不是以冲突管理为主任务）。

### 1.4 指标与可诊断性：从单一准确率到"端到端 + 分解"
- **PersonaMem**：以 **四选一判别准确率（discriminative accuracy）** 和 **生成式 log-probability ranking** 双模式评测。按偏好类型（static vs dynamic）、任务领域（15 个场景）分层统计，可诊断模型在哪类偏好/场景上更弱；不依赖 LLM judge，人类验证质量高达 90%+ 一致性。
- **LongMemEval**：以 **最终 QA accuracy** 为主，同时用 **recall@k** 等诊断检索效果，并指出"检索到了也不一定会用"（reading 是瓶颈）。
- **Mem-Gallery**：按子任务采用 accuracy/F1/检索类指标，对 13 个 memory 系统做系统对照，突出"推理与知识管理"短板。
- **KnowMe-Bench**：分层正确性 + **证据集合**审计（可解释性/抗幻觉导向）。
- **LOCOMO**：三任务（QA/事件图总结/生成），强调传统生成指标不足以测长程理解，并用对抗题暴露结构性错误（说话人/事件错绑）。

## 2. 关键对比维度（Benchmark × 方法的统一坐标系）

1) **记住什么（Memory content）**  
- 从 **事实/偏好/事件（LongMemEval）** → **动态偏好演变（PersonaMem）** → **时间/因果链（LOCOMO）** → **多模态证据（Mem-Gallery）** → **动机与原则（KnowMe-Bench）**。

2) **何时更新/遗忘（Update & forgetting）**  
- PersonaMem：将"偏好演变"显式化为评测核心——干扰项包含过时偏好，模型必须识别"用户已变"。  
- LongMemEval/Mem-Gallery：把 **冲突/更新/拒答**变成评测硬约束，逼方法做"语义治理"。  
  
3) **如何评测（Evaluation philosophy）**  
- PersonaMem：判别（四选一 accuracy）+ 生成（log-prob ranking）双模式；按 static/dynamic 偏好分层诊断；不用 LLM judge。  
- LongMemEval：端到端 accuracy + 分解诊断（recall@k / reading strategy）。  
- Mem-Gallery：功能维度任务矩阵，覆盖抽取/推理/管理的"系统全栈"。  
- KnowMe-Bench：evidence-linked 的可审计推断，抑制幻觉与无依据"心理分析"。  
- LOCOMO：三任务综合，强调对抗题与因果/时间理解。

4) **规模化问题（Scaling bottlenecks）**  
- **百万 token**（LongMemEval-M）暴露长上下文与记忆系统的稳定性上限。  
- **多模态存储/检索成本**（Mem-Gallery）成为效率瓶颈。  
- **检索噪声与读用失败**：即使 recall 高，reading 仍掉点（LongMemEval 指出）。  
- **时间对齐困难**：对话中表现为说话人/事件错绑（LOCOMO），叙事中表现为闪回误锚定（KnowMe-Bench）。

## 3. 各方案优劣势总结（面向选型）

- **PersonaMem**：最直接测量"**动态偏好追踪与个性化**"的 benchmark；180+ 用户 × 15 任务的规模化设计配合 session 拼接机制，既可测 128k 也可测 1M 上下文；揭示了即使 GPT-4.5/o1 等前沿模型也仅 ~50% 的准确率，明确了"偏好演变追踪"是当前瓶颈。适合评估个性化助手的用户画像建模能力。 
- **KnowMe-Bench**：适合研究"从记忆到人理解"的跃迁（解释/原则/动机），对 evidence-grounded 方法特别友好。  
- **LongMemEval**：最接近"真实助手长期交互"且维度全面；适合评估产品级记忆系统全流程。  
- **Mem-Gallery**：如果目标是 MLLM/多模态助手，这是目前最"功能完备"的多模态长期记忆评测框架之一。 
- **LOCOMO**：适合评估"超长对话一致性 + 时间/因果理解 + 对抗鲁棒性"，尤其能暴露说话人/事件归属错误。

## 4. 发展趋势总结与预测

- 领域正在从"**长上下文（long-context）**"转向"**记忆系统化（memory as pipeline/OS）**"：LongMemEval/Mem-Gallery 把 indexing-retrieval-reading 与 knowledge management 显式化后，单纯把窗口变长无法覆盖更新/冲突/拒答与读用失败等问题。  
- **动态偏好追踪是当前最被低估的瓶颈**：PersonaMem 揭示即使最强前沿模型在"识别用户偏好已发生变化"这一任务上也仅约 50% 准确率，且 reasoning 模型（o1/o3-mini/o4-mini/DeepSeek-R1）并未比非 reasoning 模型有优势——说明问题不在"推理能力"而在"长程信息定位与时序归因"。
- Benchmark 未来大概率收敛到两类"硬约束"：  
  1) **全流程可诊断**（不仅测答案，还测检索、读用、更新、拒答）；  
  2) **证据约束与审计**（KnowMe-Bench 风格）以抑制幻觉与无依据个性化推断。  
- **个性化评测正在从"静态画像匹配"走向"动态画像追踪"**：PersonaMem 的 static vs dynamic 偏好分层评测设计，以及 session 拓扑排序+交错拼接的数据构造方法，为大规模个性化评测提供了可复现的 pipeline。
